# AGENTS.md — IndietroTuttaBackend (Express + Turso + Leaflet)

Web backend + live map + boat panels + OTA host for ESP32 devices.
Prod: `https://indietrotutta.onrender.com`. Local: `node server.js` → `:3000`.

## Stack / entry

- `server.js`: cors + `express.json()` + `public/` static, mounts `gps,health,devices`, then `initDb().then(listen)`. Falls back to in-memory mode if no `TURSO_DATABASE_URL`.
- Deps: `@libsql/client ^0.17.4`, `express ^5.2.1`, `cors`, `dotenv`, `node-fetch`, `nodemon`.
- `config.js` only exports PORT. `.env` (gitignored, required): `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`, `REDPLOY_HOOK_URL` (note typo REDPLOY). Render env mirrors it.
- `store/db.js`: `getClient()` / `initDb()` creates `devices, gps_points, courses, sessions, session_boats, runs, signals, session_results` (+ gps indexes; `devices` migrates `firmware`/`boat`/`ip` TEXT + `mock` INTEGER; `sessions` migrates `windSpeed` REAL; `courses` migrates `buoyDiam` + `simRoute` TEXT). No row cap. Connection test `SELECT 1` throws on bad token.
- (Race program live: `courses` (wind-frame shapes) → `sessions` → scripted `sim` → device race screen. The shape table has been renamed twice (courses → templates → courses); `races` dropped. See root AGENTS.md.)

## Stores (all have in-memory Map fallback when DB missing)

- `deviceStore.js`: `upsertDevice(deviceId,{username,firmware,ip})` preserves `firstSeen` (captures LAN `ip` from heartbeats); **`mergeIp()` keeps a known LAN address over a loopback heartbeat** — on Render every request arrives through the proxy as `127.0.0.1`, and storing that used to wipe the address a local heartbeat had learned, which is exactly what `POST /boats/:id/server` and the mock toggle need to reach the portal (a loopback address says nothing about where the boat is); `setDeviceMock(deviceId,on)` records assumed mock-GPS state without touching `lastSeen` (no fake live). Username `/^[A-Za-z0-9 ._-]{1,32}$/`, firmware `/^[A-Za-z0-9._-]{1,16}$/`, boat `/^[A-Za-z0-9 ._-]{1,64}$/` (bad values keep old). `renameDevice(deviceId,{username,boat})` edits info without touching `lastSeen` (no fake live). **`ensureDevice(deviceId, fictiveName)`** (todo 55) is the create-path recorder: a participant the server has never seen gets a row immediately under a fictive name (`fictiveName()` → `Boat EE99`, last four id chars), `INSERT OR IGNORE` so a real row is never overwritten, and `lastSeen = ''` because `devices.lastSeen` is NOT NULL and a declaration is not a heartbeat (`computeStatus("")` → `offline`, the boat list prints `-`). `getDevices()` adds `status: live<90s / idle<10m / offline`. `deleteDevice` also deletes its gps_points.
- `gpsStore.js`: `addPoint({deviceId,username,lat,lon,speed,course,altitude,sats,timestamp,receivedAt})`. `getPoints({date,deviceId,start,end})` — `start/end` ISO range takes precedence over `date` (YYYY-MM-DD on `substr(timestamp,1,10)`), `ORDER BY id ASC`. `getLatestPoint(deviceId?)`, `getPointCount()`. (Waypoints/flagged are GONE: no `flagged`/`uid` columns — dropped by a guarded migration in `initDb`.)
- `simShape.js` (**todo 32**): the scripted route as a property of the course SHAPE. `shapeOfCourse` (a course row), `shapeOfSession` (frozen `courseSnapshot` for the marks + `windFrameSegment` for the lines), `shapeWaypoints` / `compileShapeRoute` (every single mark gets a CCW-for-`P` / CW-for-`S` rounding at `roundingM` — the boat always goes around the buoy, never cuts the corner; a gate the course comes back through is rounded CCW around its first buoy, a threaded gate keeps its crossing point), `shapeKey` (hash of the shape + radius + compiler version — the cache's invalidation), `resolveRoute` (rotate by wind, scale, translate), `analyzeRoute` (the offline proof of the device rule, shared by `tools/draw-routes.js` and `POST /courses/sim-route` (normative spec, LOCKED: ../IndietroTutta/SPEC-mark-passing.md): per mark the exit-traverse crossing toward the next mark, which side of the axis it is on — right facing the next mark = P/CCW — and whether the entry traverse was cut arriving; gates score by cutting the buoy-pair segment; no distance minima, `dist` is informative only), and the cache-aware `routeForSession` / `routeForCourse` (read `courses.simRoute`, compile on a miss, store only when the session sails the course's *current* shape). The offset is part of the shape, so it would scale with the course — but the pass distance exists for the DEVICE's sake (its 1Hz sampling has to see a traverse at all), so `roundingM` means REAL metres everywhere in the code and `shapeRoundingFor(roundingM, scale)` converts to shape metres at the compile boundary: a session at `scale 0.3` gets a 100 m shape radius and still passes 30 m off the buoy (`clampRounding` range 5..200). Distances that exist for the device's sake (200m finish overrun, 300m hold) stay in `store/sim.js` as fixed metres. See ROADMAP todo 32.
- `standings.js` (**todo 3**): the race table. `rankRows(boats, runs, signals)` is pure — `tools/check-standings.js` proves it without a DB — and is the ONE place the order is decided: corrected = elapsed + the SCP seconds raised against that boat, a `DSQ`/`DNF`/`RET` **signal** outranks the run's own `result` (the committee can disqualify a boat that crossed the line), order is finishers by corrected → boats still racing (no run uploaded) → DNF/RET → DSQ, and **only finishers carry a rank** (`null` → "–", as the results table always printed). `computeStandings` reads boats + runs + signals; `finalizeStandings` freezes the result into `session_results`; `getStandings` answers `{final, computedAt, standings}` - `final:true` only when a snapshot exists, so the pane's PROVISIONAL/FINAL tag is the presence of stored rows, not a second rule - **and it re-freezes a snapshot whose boats are not the session's boats** (todo 55; a read that writes, so it logs). `saveStandings` **replaces** the set (an empty table clears an old one), and `deleteStandingsForSession` is the delete cascade. Not a series: one session, one table.
- `simPlayer.js` (**todo 63**, compressed by **66**): the sandbox — a simulated session sailed by the BACKEND, no device on the other end. `start({sessionId,boats,timeScale})` requires the session to be `simulated` and still scheduled/live, drops whatever `/sim/runs` already scripted (auto-sim), compiles one run **per boat** with its own `speedKn`, refuses a fleet whose guns differ by >1 s, then plays each tape into `POST /gps` over HTTP **as that boat's `DeviceId`** (the device's own request minus the screen: calling `addPoint` directly would skip `upsertDevice`, the `simulated` tag and `racingPersist`) and uploads the run at its own finish. **The tape is played in WINDOWS** (todo 66): every fix whose due time falls inside the next `BATCH_MS` (800 ms) of wall clock rides one `POST /gps` call and one batched INSERT, each fix keeping its own tape timestamp — a single round trip measured **~415 ms**, so one-per-fix capped the sandbox near 2x whatever `timeScale` asked. At 1x a window is one fix (the tape is 1 Hz), so a wall-clock race is unchanged; the granularity cost is that the live map steps once per window (at 50x that is ~40 s of race time per refresh). Measured on a 150-fix tape, 2 boats (local, live Turso): **1x 155 s wall, 10x 19 s, 50x 6.5 s**, every fix played and every run recording the tape's own elapsed. Scored: **start + finish only**, so `splits: []` is expected — the tape carries no mark passes, and passes are 64's work. `status()` never 404s (a pruned player answers `running:false`); `stop()` halts the loops, drops the scripts and **abandons the session only while the race is still open** (a fleet that already uploaded derived `finished`, and abandoning it would void a sailed race). RAM only, like the scripts: `sweepOrphanedSimSessions()` runs from `server.js` before `listen` and abandons any simulated session still reading scheduled/live with no player — otherwise a restart leaves it `live` for ever (the session-250 pattern). The clock factor is clamped by `sessionStore.MAX_TIME_SCALE` (**50** since 66; the UI offers 1/10/25/50 and the number is stored on the session and shown in its panel). A sandbox fleet is capped at `MAX_BOATS` **10**: the first ten sail and any extra declared boats are **dropped with a warning** (user, 2026-11-05) rather than refused — note that a trimmed fleet leaves those extra participants without a run, so such a session cannot derive `finished` on its own; stop it (abandon) or prune it. `tools/check-simscale.js` is the proof: it sails the same course at the scales you name and asserts every run's elapsed equals the player's tape-derived number while the wall time stays short — a compressed race must never be timed by the wall clock.

## Routes (every new route needs `bruno/*.bru`)

- `GET|POST /health` — heartbeat: `upsertDevice` from `DeviceId`/`Username`/`Firmware-Version` headers (POST also body incl. `fw`), returns `{status, storedPoints, deviceId, heartbeat, serverTime}`. GET also piggybacks `session` (assigned scheduled/live session: id/mode/status/startTime/courseVersion/windDir/windSpeed/marks/startLine/finishLine/signals; null when unassigned) and `wind` `{dir,speed}` — venue wind from the boat's last stored point via the `store/wind.js` chain, stale-while-revalidate per device (10-min TTL / >2 km drift / first poll; session wind wins on the device).
- `gps.js`: `POST /gps` (validate lat/lon numbers, store + upsert device; `simulated` uploads ALWAYS feed the ephemeral single-point overlay AND **also persist to `gps_points` while the boat is racing** (todo 9), tagged `simulated: 1` so map styling and stats can tell them apart — so a finished mock session DOES have a Turso track, it is just simulated; `racingPersist(deviceId)` gates the persistence with a short cache; a **`{points:[...]}` batch** (todo 66) is the same contract for the sandbox: DeviceId header, 1..500 fixes, `simulated` forced, one device upsert and ONE batched INSERT, each fix carrying its own timestamp — it exists because a per-fix round trip measured ~415 ms and capped the player near 2x), `GET /gps/sim-live?deviceId=` (latest sim point only, no history — refresh picks up upcoming fixes exclusively), `GET /gps?date=&deviceId=` or `?start=&end=`, `GET /gps/latest?deviceId=`, `GET /gps/days?deviceId=` (days with data + counts for per-boat calendar). Also keeps `devices.mock` in sync from the `simulated` field — transition-only writes, so the mock flag is reliable without a device change. No flagged/waypoint routes (removed 2026-10-09).
- `courses.js`: `GET /courses` (the whole library — five seeded built-ins first via `builtinKey`, then user courses alphabetically), `POST /courses` (`{name,desc?,owner?,marks,startLine,finishLine}` — lines are MANDATORY, missing lines or `start`/`finish`-type pins are 400), `GET/PUT/DELETE /courses/:id` (PUT bumps `version`; **403 on a built-in** — they are read-only, copy-only), **`GET /courses/:id/sim-route`** (the compiled scripted route for this course's SHAPE, wind-frame metres, `{key, roundingM, cached, shape, wps}`; `?roundingM=` recompiles at another pass distance) and **`POST /courses/sim-route`** (`{marks,startLine,finishLine,roundingM?}` — the same compile for a shape that is NOT saved, validated with the course rules so a lineless draft 400s; nothing is stored, `-> {roundingM,key,wps,passes}`). `passes` is the read-out the course editor draws: per mark which side of the exit traverse is cut toward the next mark, and whether the entry traverse was cut arriving (no distance minima — see `analyzeRoute` in `store/simShape.js`). The five built-in shapes live in the same table, seeded once from `store/courseStore.js` (`seedBuiltinCourses`, idempotent). Optional line segments `{ax,ay,bx,by,square?,bias?}` (≥5m, square-to-wind default); `finishLine` may be `{sameAs:"start"}`. Geometry convention: **+y = upwind**, the start/finish line sits at `y=0` (leeward edge) and the course runs upwind from it.
- `sessions.js`: sessions encapsulate courses (frozen snapshot, never linked). Status is inferred on read (abandoned sticks; finished when every boat uploaded a run — boats only, so a
  boat-less session can never finish; live once the gun passes, boats or not; else scheduled) — `PUT` accepts only `abandoned` (or `scheduled` to re-open). **DELETE cascades (todo 33):** the session's `runs` (results), `signals` and persisted `sim_routes` row go with it, plus its `session_boats` — all keyed by `sessionId`, so leaving them is invisible garbage. The response reports the counts (`{status:"deleted",runs,signals,routes,results}`); children go first so a failure leaves the session in place and the delete can be repeated. `node tools/prune-db.js` sweeps what older builds orphaned. **One active session per boat:** `createSession`/`repeatSession` reject (409, message names the blocking session) when a boat is already in another scheduled/live session. **Auto-sim:** a boat that is currently `mock` auto-starts its scripted run (`store/sim.createRun`). **Participants are declared ONCE, at creation (todo 55):** there is no `POST/DELETE /sessions/:id/boats` any more (removed 2026-10-22, Express answers 404) and no UI control — the boat list is part of what was created, like the geometry and the gun. Reasons: a late add to a *finished* race un-finishes it (status is derived, so "every boat uploaded" goes false → `live`, back on the health piggyback, todo 30 auto-page), and it left the frozen table describing a different fleet. An unknown participant id is recorded immediately by `ensureDevice` as `Boat XXXX` (see `deviceStore`). `windSpeed` (kn, optional) is stored and pushed via health. **`simulated` (bool) and `timeScale` (number, 1..50)** mark a session the backend sails itself (todo 63, compressed by 66): both are stored columns, both ride the list and the detail (`sessionListRow` + `rowToSession`), a repeat carries `simulated` and resets `timeScale` to 1, and `timeScale` is 400 above `MAX_TIME_SCALE` (50). `GET /sessions[?date=]`, `POST /sessions` (`{courseId}` or `{snapshot:{marks,startLine?,finishLine?}}` + placement → resolved marks; stamps `courseShapeVersion`; **`boats:[{deviceId}]` is the only way to declare participants**, same 409 guard + auto-sim, one round trip; a nonzero `startOffsetSec` is a 400), `GET/PUT/DELETE /sessions/:id` (geometry edits re-resolve + bump the session's own `courseVersion`), `POST /sessions/:id/repeat` (same frozen shape onto a new day, boats carried over — a new session, so still a declaration). Run uploads: `POST /sessions/:id/runs` (device finish log `{deviceId,startEpoch,finishEpoch?,splits?,events?,result?}`, re-upload replaces), `GET /sessions/:id/runs` (results, finished first). Committee: `POST /sessions/:id/signals` (`{kind: OCS|DSQ|DNF|RET|SCP|RECALL|ABANDON, deviceId?, detail?}`), `GET /sessions/:id/signals` (log, oldest first). **`GET /sessions/:id/standings`** (todo 3): `{final, computedAt, standings:[{deviceId, rank, result, elapsedSec, penaltySec, correctedSec, splits}]}` — `final:true` is the snapshot frozen into `session_results` by the event that closes the race (the run upload **or** a terminal `DSQ`/`DNF`/`RET` signal, which ends a boat's race without any run), written BEFORE the event is announced so a client reloading on it sees the final table; `final:false` is computed on the spot. A finished race with no snapshot is frozen on first read (backfill — those rows predate the feature, and the pane's FINAL tag is the presence of a snapshot). **A snapshot whose boats are not the session's boats is never served** (todo 55): a closed race is re-frozen on read (logs `[standings] session N: …`), a race still running loses the stale snapshot and reads `PROVISIONAL`. With participants fixed at creation, such rows are not a record of anything, and `node tools/prune-db.js --standings` sweeps old ones in bulk. Re-opening a session (`PUT {status:"scheduled"}`) drops the snapshot; `DELETE` cascades it too and reports `results`.
- `wind.js`: `GET /wind?lat=&lon=[&provider=auto|wu|wc|om]` — suggest-only venue wind (WU PWS `WU_API_KEY` → Weathercloud unofficial → Open-Meteo model), 10-min cache keyed by `lat,lon,provider`; `provider` forces a single source (502 `no data from provider 'x'` when it has none, 400 on an unknown name); caller freezes value into session.
- `sim.js` (in-memory test rig, lost on restart): `POST /sim/runs {sessionId, deviceId?, speedKn?, startInSec?, roundingM?}` compiles a 1Hz scripted route (hold 300m behind the line → gun cross ~8s after the gun → a fixed-radius pass (default **30m**, per-call override) on each mark's required side, gate pairs threaded near the first buoy → finish + 200m overrun, seeded noise; default **14 kn**, clamped 1-40). Both defaults are deliberate and about the SAMPLER, not about realism: at 1Hz a 30m rounding is sampled by many fixes (a 15m arc by two or three) and 14kn puts ~7m between fixes, where 28kn put ~14m — the fix spacing was the coarsest thing in the system. The **geometry** comes from `store/simShape.js`, compiled once per course SHAPE and cached on the course row (todo 32) — the sampler here owns speed, gun, the pre-start hold and the sampling, all metres in real water. `GET /sim/next?deviceId=` wall-clock delivery, **`GET /sim/tape?deviceId=&runId=&from=&n=`** the same journey as ONE CSV tape (`#runId,sessionId,gunSec,durationSec,total,serverEpoch`, then `epoch,lat,lon,speed,course` per fix) — the device plays it from RAM at 1Hz and gates it on `sessionId` (a journey must not sail before the engine holds its session and the race screen is up, or it wastes its front), so a slow or late fetch costs the START of a mock race instead of a hole in the middle of one; with no live run the same URL carries 30 fixes of the **wander** (`runId` `wander`), so the device needs one URL and one reader whatever the mock is doing, `GET /sim/runs[?sessionId=]`, `DELETE /sim/runs/:id`, **`GET /sim/routes/:sessionId`** (the route keyed by SESSION, served from `store/simRoute.js` — session-keyed because the frontend only holds a session id, and a run is pruned 10 min after it ends, so a run-id lookup 404s exactly when a finished race is being inspected), `GET /sim/wander?deviceId=` server-driven wander fix (**viewport anchor when pushed → else this boat's own newest stored point → else the newest point in the DB**; 404 only when the DB has nothing at all). The DB fallbacks seed the walk **once**, on the first poll for a boat — the 1Hz poll never queries the DB. After seeding, with no browser anchor, the walk is free; `seededFrom` in the response says which rung was used, `POST /sim/anchor {lat,lon}` sets the viewport anchor. **The script overruns the finish line by 200m along the incoming bearing** — the route's last waypoint is the line's centre, so stopping there left the side flip that scores a finish on a single sample (the last of the run) and every mock race ended on the device's "past line, no clean cross" escape hatch.
- **`POST|GET|DELETE /sim/players[/:sessionId]`** (**todo 63**, the sandbox — same rig, but sailed by the SERVER with no device): `POST {sessionId, boats?:[{deviceId,speedKn}], timeScale?}` → 201 the player status (one engine run per boat, every fix replayed into `/gps` as that boat's `DeviceId`, run uploaded at its own finish); `GET` → `{sessionId, running, timeScale, startedAt, endedAt, warnings, boats:[{deviceId, runId, speedKn, played, total, startEpoch, finishEpoch, elapsedSec, uploaded, failed, done}]}`, or `{running:false, boats:[]}` when nothing is sailing it; `DELETE` → stop + abandon. The session must already exist with `simulated: true` (the UI's Simulate switch does it), participants are declared at creation as always (55), so `boats` may only name boats already in the session and omitting it sails every one of them at 13.5/14.5 kn. `timeScale` above 1 is a **400** until 66. Best gate: `node tools/prune-db.js --sim-sessions` lists what a sandbox race left behind.
- `devices.js` (+ `/boats` alias): `GET /devices`, `GET /boats`, `PUT /devices/:id` / `PUT /boats/:id` rename `{username, boat}` (no heartbeat side effects), `POST /devices/:id/mock` / `POST /boats/:id/mock` `{on:bool}` (proxies to the device portal `/mock` over LAN via stored `ip`, then records `mock`; 409 no known ip, 502 portal unreachable), **`POST /devices/:id/server` / `POST /boats/:id/server`** `{mode:"prod"|"dev", host?}` — the boat-info pane's PROD/DEV switch, a thin passthrough of the device's own REST call `POST /server?mode=…&host=…` (409 no known ip, 502 portal unreachable; 400 on a bad mode/host). `mode=dev` with **no host** fills in this backend's own LAN address + port (`backendLanHost()`: first non-internal IPv4, skipping link-local and Tailscale CGNAT, 192.168 > 10 > 172.16/12), because that IS the machine the boat must talk to — `localhost` is meaningless to a device. Nothing is stored: the device owns the choice in NVS `srv` and the response is its own `{mode, host, base}`. **`GET /devices/:id/server` / `GET /boats/:id/server`** reads that state back (a passthrough of the portal's `GET /server`), so a page reload shows the real mode instead of the last switch made from that browser; same 409/502 shape. `DELETE /devices/:id` (+ `/boats/:id`).

## Bruno / verify / deploy

- `tools/` (dev helpers, not routes — no `.bru` needed):
  - `check-bru.js [dir]` — the `.bru` linter (defaults to `bruno/`): grammar (one request per file, known blocks, no BOM/bare markdown) **and wiring** (every `:param` in a url declared in `params:path`, no undefined `{{var}}`, no bare `params { }`). The wiring half exists because `sim/run-route-by-session.bru` parsed fine and still sent `/sim/routes/%7B%7BsessionId%7D%7D` → 400. It cannot see **id rot**: run the request.
  - `prune-db.js [--yes] [--orphans] [--sim-gps] [--standings] [--sim-sessions] [--sim-devices]` - the operator sweep for the **five** kinds of invisible garbage: **orphans** (`runs`/`signals`/`sim_routes`/`session_boats` rows whose `sessionId` no longer exists - what builds before todo 33's cascade left behind), **simulated GPS** (`gps_points` where `simulated=1`, i.e. mock uploads persisted while racing, per todo 9 - a few hundred per mock race), **stale standings** (a `session_results` snapshot whose boats are not the session's `session_boats`, matched as sets; the sweep drops them, and the next standings read recomputes - this is where session 231's one-row FINAL table was found), **simulated sessions** (`sessions.simulated = 1`, todo 63: a race the backend sailed itself - deleted through the session cascade, so its runs/routes/frozen table go with it) and **sandbox boat rows** (`devices` with the `AA:BB:CC:DD:*` prefix that no `session_boats` row names any more, todo 66 - every sandbox test used to leave its phantoms in the boats pane, tickable and never sailing again). Real fixes are never touched. **Dry run by default**; `--yes` executes; no category flag means all five. No export: `--yes` is the only safety rail, and it talks to the LIVE Turso DB that prod reads.
  - `new-mock-session.js [distM] [gunSec] [courseId] [windDir] [scale] [--boats id1,id2] [--at lat,lon]` — creates a scripted session laid out the way the **device** does: the line `distM` metres UPWIND of the boat, never on top of it. The boat then waits outside the 150m OCS band instead of on the line, where a metre of jitter read as a crossing. Reads position from `/gps/sim-live` **first** — a mock boat never reaches Turso, so `/gps/latest` is the last REAL fix, days old and km away. **`scale` defaults to 0.3**: a full-size W/L mock race is 431s and most of it is legs nobody is testing, a 0.3 course is 239s, and the pass distance does not shrink with it (`roundingM` is real metres — see `store/simShape.shapeRoundingFor`). Pass 1 to sail real size. **`--boats` REPLACES the participant list** (default: `DEVICE_ID` alone) — todo 55 made participants a creation-time decision, so there is no add-boat route and a fleet has to be declared here. **`--at lat,lon`** places the line without asking the backend where a boat is, which is what a device-free bench needs.
  - `check-route.js [sessionId]` — recompiles a real session and checks it against the rules the **device** scores by (the traverse law in `../IndietroTutta/SPEC-mark-passing.md`): per mark the exit traverse crosses the mark's axis on the required side toward the next mark, gates by cutting the buoy-pair segment, and a finish crossing that is *sustained* — two consecutive fixes on opposite sides with the interpolated crossing inside the line's span. Exits non-zero, so it can gate a change to `compileScript`. The "sustained" part is what catches a flip that exists only on the final sample — the real bug.
  - `check-ocs.js [sessionId]` — replays the approach through the device's OCS predicate (transcribed from `race_run.cpp`) twice: as sailed (must stay silent) and shifted so the boat crosses 20s early (must raise OCS). A quiet OCS detector is a worse bug than a noisy one, and a green mock race cannot tell them apart. Move the **samples**, not the gun — moving the gun closes the pre-gun window before the boat reaches the line and reports a failure that is an artefact of the test.
  - `race.sh [distM] [gunSec] [courseId] [windDir]` — one race end to end. Verifies the device is on the race screen via `sys.page` before creating anything, snapshots the 200-line serial ring to a file every 4s, and stamps `LINK LOST` if the portal or backend goes away — a **laptop suspend kills the local backend and the race with it**, and an unmarked partial race is indistinguishable from a firmware bug.
  - `check-standings.js` (todo 3) — the standings RULES, proved without a
    server or a DB: corrected time (elapsed + SCP), a penalty heavy enough to
    swap the lead, a committee DSQ beating a `FINISHED` run, DNF/RET after the
    finishers, an upload-less boat still `RACING`, and the signals that must be
    ignored (fleet-wide, or for a boat that is not in the session). A wrong
    table looks plausible — it is just names in some order — so every rule has
    a case, and the same `rankRows()` is what the route calls.
  - `check-participants.js` (todo 55) — the FLEET proved **without a device**:
    two boat ids the server has never seen, driven entirely over HTTP. Declares
    them on `POST /sessions` in one call, checks they land as `Boat EE11`/`EE12`
    with `lastSeen = ''` (a declaration is not a heartbeat), that
    `POST/DELETE /sessions/:id/boats` are 404, that a busy boat is refused 409,
    that `repeat` is refused 409 while the fleet is still racing and carries the
    boats once it closed, that a raw-INSERTed ghost `session_results` row is
    never served (heal on read), and that the table freezes with both boats
    ranked only when every declared boat uploaded. `check-standings.js` proves
    the order without a DB; this proves the fleet against a live server. It
    creates and deletes two sessions + two device rows on whatever DB the server
    is on — the `finally` block prints the cascade counts so a failed cleanup
    is visible. 23/23 on 2026-10-23.
  - `mock-fleet.js` (todo 56) — **the fleet sailed with no device at all**: the
    bench is the DEVICE minus the screen. Creates a two-boat session through
    `new-mock-session.js --boats` (participants cannot be added later), one
    `POST /sim/runs` **per boat** with its own `speedKn` (a deviceId-less call
    gives every boat the same speed and the fleet ties), fetches each tape,
    then plays every fix into `POST /gps` with that boat's `DeviceId` and
    `simulated:true` at the recorded cadence, and uploads the run at the finish.
    `--speed N` compresses (default 1x wall clock); `--no-run` sails without
    uploading; `--at lat,lon`, `--gun`, `--dist`, `--course`, `--scale`,
    `--speed-kn a,b` pass through. Four traps it encodes: the **last** line
    crossing is the finish (a W/L's finish line *is* the start line, so the
    first sustained flip is the start), the tape's last sample is the 200 m
    finish **overrun** (elapsed is line-to-line), a run created <15 s before the
    session's `startTime` silently gets `now+60s` (all guns are checked equal),
    and `POST /sessions` auto-scripts boats already flagged `mock` (those runs
    are dropped first — a second bench run would otherwise sail two scripts).
    It prints the standings and exits non-zero if the table is not FINAL with
    one row per boat. **~400 ms per fix**: the cost is the server's per-upload
    device upsert against Turso, so above ~2x the bench reports the achieved
    rate instead of honouring `--speed`.
  - `check-simscale.js [--course=34] [--scale=0.12] [--gun=30] [--boats=2] [--scales=1,10,50] [--at lat,lon] [--keep]` (todo 66) — **the sandbox's proof that speed does not change the race**: it creates one simulated session per scale, starts the player on each, and asserts every run's `elapsedSec` equals the player's tape-derived `elapsedSec` while the wall time stays short. Each session compiles its OWN tape (the sampler seeds per creation), so comparing two runs' elapsed would compare two different races — the invariant is per run against its tape. It also prints the wall time and fixes played, which is the throughput measurement (1x 155 s, 10x 19 s, 50x 6.5 s on a 150-fix tape, before/after the batched `/gps` window). Sessions are deleted unless `--keep`; the 1x pass is real time.
  - `draw-routes.js [id...]` (todo 32) — **writes one PNG per course into `out/sim-routes/` (+ `index.html`)**: the course shape from above (x right, y upwind, the same view as the builder), the scripted route, the pass point and side at every mark, and the `giro` — how far the buoy rotates around the boat while it passes, the number the device scores on (150° threshold). It also flags a mark the boat sails *over* somewhere else on the route (e.g. a leeward mark sitting on the finish line), which is worth seeing because the device may count it. No server needed; it reads the courses straight from the DB. This is the "check the route by eye, course by course" tool — a course is easier to point at by name than by id, and the figures carry both.

- **Destructive schema changes: never drop a column while the OLD build is still live.**
  2026-10-09: dropping `gps_points.flagged` locally killed prod (`SQL_INPUT_ERROR: no such
  column: flagged` at `store/db.js:94`) because the deployed build still selected it — every
  DB-backed route 500'd until `sc` redeployed the new code. Safe order: (1) deploy code that
  stops using the column, (2) drop it in a later deploy (or keep it one release). Local
  `:3000` shares the LIVE Turso DB, so a local migration IS a prod migration.
- **A RENAME cuts both ways: the old build renames the table BACK on every cold start.**
  2026-10-10: renaming `templates`→`courses` locally worked, then Render spun the instance
  down; the wake-up ran the deployed build's `ALTER TABLE courses RENAME TO templates` +
  `sessions.templateId`, silently reverting the migration. Prod stayed healthy (old code +
  old names = self-consistent) while **local `:3000` broke** with `no such table: courses`.
  Lesson: a hard rename has a hard deploy dependency — the backend must ship in the same
  round as the schema. Until then local DB work is a treadmill (each prod cold start undoes
  it), so verify with `SELECT name FROM sqlite_master` + a `PRAGMA table_info`, not with
  `/health` (health doesn't read the renamed tables and looks fine).
- **A stray `DeviceId` header rewrites a device's recorded LAN `ip`.**
  `upsertDevice` takes `ip` from `req.ip` on every `/health` and `/gps`, and
  identity is the unauthenticated `DeviceId` header by design. So
  `curl localhost:3000/health -H "DeviceId: 08:…"` — the obvious way to poke
  the endpoint by hand — makes the backend record `127.0.0.1` as that boat's
  address, because the request came from loopback (`cleanIp` maps `::1` →
  `127.0.0.1`). The next real heartbeat fixes it, but until then
  `POST /devices/:id/mock` proxies the portal request to loopback and fails,
  and it looks like the device moved. **Read `/devices` before using the `ip`
  for anything, and never "verify" `/health` with a spoofed DeviceId.**

- **`ALTER TABLE ... RENAME COLUMN` breaks on a table grown by many `ADD COLUMN`s.**
  SQLite re-parses the accumulated schema and fails with `duplicate column name:
  courseShapeVersion`. `initDb` now **rebuilds** `sessions` into its canonical shape
  (rename → `sessions_legacy`, copy with per-column source aliases, drop) whenever a
  legacy `template*` column is still present. Prefer a rebuild over a rename for tables
  that have been migrated repeatedly.
- **`ABANDON` is session-scoped, so raising it stores `status='abandoned'`.**
  Status is otherwise inferred on read, so without that an abandoned session kept being
  inferred scheduled/live: it stayed on the health piggyback (a device that walked away was
  handed the session straight back) and kept the boat blocked from starting a new one.
- **Never rewrite `public/*.js|css|html` with PowerShell `Set-Content`/`Out-File`** — they
  default to a legacy codepage and silently double-encode every non-ASCII char (UTF-8 → CP1252
  → UTF-8), so `·` becomes `Â·`, `→` becomes `â†’`, `×` becomes `Ã—`. The file stays *valid*
  UTF-8, so a validity check passes and the browser faithfully renders the garbage — it looks
  like corruption in the wind pane, top bar, boats and courses all at once (hit 2026-10-09:
  131 sequences in `app.js`, repaired in `fb75ce4`). Use the edit tool; if a shell write is
  unavoidable go through Node (`fs.readFileSync/writeFileSync(..., "utf8")`).
  Repair/verify recipes (Node, not PowerShell — the console mangles the literals):
  decode the mojibake run through **windows-1252 → bytes → UTF-8**, and accept a result only
  if it is valid UTF-8 with no control chars. A plain latin1 pass has no such guard and turns
  correct `—`/`…`/`•` into `\u0014`/`&`/`"`. Degree signs in rendered HTML: prefer the ASCII
  entity `&deg;`.
